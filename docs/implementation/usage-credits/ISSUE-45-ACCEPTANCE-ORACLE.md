# Issue #45 independent acceptance oracle

This oracle is independent of the implementation. It defines what Codex must prove before closing
#45. Issues #43 and #44 must already be accepted because #45 depends on both.

## Minimum architecture

1. Extend the deep `usage-account.ts` module from #43.
   - Each `UserDurableObject` SQLite store remains the authority for balances, the Credit Ledger,
     idempotent operation results, and the registration outbox.
   - Add administrator `grant`, `deduct`, `reconcileBalance`, and `reverse` operations to that module.
   - Complete every financial mutation in one `transactionSync()` call.
   - Keep `user.ts` as a thin delegate. It must not duplicate accounting rules.

2. Add a logically separate authoritative User Registry.
   - The smallest design is a separate registry collection in the existing strongly consistent
     `AdminSettings` singleton Durable Object. It must remain a different authority and data set from
     the replaceable Usage Projection added later.
   - Store only directory data: a stable User reference, User DO id, searchable identity fields,
     first registration and activation timestamps, and the registration event id.
   - Do not use KV, analytics, logs, or the Usage Projection as the directory authority.
   - If the implementation creates a separate `UserRegistryDurableObject`, it must add a SQLite
     migration, regenerate Worker types, and verify the release manifest. This larger deployment
     surface needs a concrete reason.

3. Initialize and register through a transactional outbox.
   - On the first authenticated access or internal Metered Use, obtain the initial-grant snapshot
     from #44's strongly consistent configuration.
   - In one User DO transaction, create or confirm the one-time initialization state, append the
     single initial-grant Credit Ledger Entry, update the balance, and write a stable registration
     outbox fact.
   - Deliver the fact to the Registry only after the local transaction commits.
   - A delivery whose acknowledgement is lost must be safe to repeat.
   - The Registry consumes registration facts. It must never issue the initial grant itself.

4. Add an administrator usage sub-capability.
   - Prefer an `AdminUsageApi` capability returned through `AdminApi`.
   - Mint it only after the existing administrator check in
     `AuthenticatedApi.getAdminApi()` (`server.ts:565-572`).
   - Bind the actor from the authenticated administrator identity. The client must not supply it.
   - The capability owns the Registry and User DO namespace. RPC accepts only ordinary serializable
     data and never returns a User DO stub to the browser.
   - Every new `workshop-shared` export has a doc comment.

5. Avoid a cross-Durable-Object call cycle.
   - A Registry or `AdminSettings` call must not hold a request while entering a User DO that can
     call back into `AdminSettings`.
   - The administrator usage capability should first resolve the target in the Registry and then
     call the User DO through a fresh stub.
   - An administrator may mutate only a registered User. It must not call `idFromName()` on an
     arbitrary client-supplied username because that could wake or fabricate a dormant legacy User.

## Financial and idempotency invariants

```text
ledger balance = sum(all immutable Credit Ledger Entry deltas)
reserved       = sum(all active Credit Reservation amounts)
available      = ledger balance - reserved
```

Administrator operations follow these rules:

- `grant(amount)` accepts a strictly positive amount and appends a positive delta.
- `deduct(amount)` accepts a strictly positive amount and appends a negative delta generated by the
  service.
- `reconcileBalance(target)` changes the ledger balance to the exact target by appending one delta.
  It never overwrites a cached balance or existing Ledger Entry.
- `reverse(originalEntryId)` appends a Credit Reversal whose delta is the exact negative of the
  stored original delta. It never recalculates from a current rate.
- An explicit administrator correction may create a negative balance. The ledger equations must
  still hold, every later paid reservation must fail, and later admin surfaces must alert on the
  negative balance. This permits an incorrect, already-spent grant to be reversed exactly.
- Administrator operations do not modify or automatically release active reservations.
- Every operation has a stable operation id. Replaying the same id with the same actor and inputs
  returns the first stored entry id, timestamp, and old/new values. Reusing it with different inputs
  or another actor fails explicitly.
- One original Ledger Entry can be reversed at most once, even when a second request uses another
  operation id.
- The actor comes from the capability, the timestamp comes from the User DO transaction, and the
  reason is trimmed, non-empty, and bounded.
- Old/new values mean ledger balance. The result or audit record also preserves the corresponding
  reserved and available values so active reservations create no ambiguity.
- Amounts use #43's exact `bigint` fixed-point representation or canonical decimal-string RPC form.
  No administrator path converts through `number`.

For this oracle, #45 reconciliation means an administrator setting the authoritative ledger balance
to an exact target through an appended compensating entry. Reconciliation of an unknown model or
Gatekeeper external outcome belongs to #51 and #63 and is out of scope here.

## Acceptance-to-evidence matrix

| #45 acceptance criterion | Required source invariant | Required executable evidence |
| --- | --- | --- |
| A new User registers once and receives the active initial grant once | Grant, balance, initialization state, and registration outbox share one User DO transaction; Registry never grants | First authentication creates one grant and one Registry row; repeated access and restart leave one of each |
| A legacy User registers and receives a grant only on first return; dormant Users are not fabricated | Only authenticated access or Metered Use triggers initialization; there is no DO namespace enumeration or bulk migration | Create legacy `created/profile` state with no usage state; it is absent before access and present after access with one grant; another dormant User remains absent |
| Concurrent authentication and retries remain idempotent | Fixed initialization id, one transaction, stable outbox id, and idempotent Registry insertion | At least 20 concurrent first accesses, a User DO restart, and delivery-after-lost-ack replay still produce one grant and one directory row |
| Administrators search registered Users without scanning Durable Object namespaces | Search reads only Registry state and uses stable order, a page bound, and an opaque cursor | Empty-query paging, case-insensitive identity/display-name search, no page gaps or duplicates, and no dormant/nonexistent User results |
| Grant, deduction, reversal, and reconciliation record complete audit data | Actor is not a client parameter; reason is required; time is server-owned; old/new balances and linked entry ids persist with the operation result | Each operation proves actor, reason, time, old/new, and links; blank reason has no effect; a response-loss retry returns the original result |
| Reversal uses a compensating Ledger Entry and preserves the original | No Ledger update/delete path; reversal delta exactly negates and links the original | Reverse a grant, deduction, or charge; original stays byte-for-byte unchanged; same-id replay is inert; a different-id second reversal fails |
| Non-admin callers cannot list Users or mutate a Usage Account | The usage capability is obtainable only from an administrator capability; every target must already exist in Registry | An ordinary User gets null from `getAdminApi()`, cannot obtain the sub-capability, and cannot make an arbitrary target create a User, grant, or Registry row |
| Tests cover lazy activation, duplicate requests, access control, and exact balance reconciliation | All rules above run against real storage and RPC | Include concurrent admin operations, negative balance, active-reservation adjustments, exact RPC above `Number.MAX_SAFE_INTEGER`, and Durable Object restart |

## Required test inventory

- New-User and legacy-User initialization paths.
- Account creation without a first authenticated return; no deployment history becomes a Usage
  Charge.
- Two authenticated connections concurrently triggering initialization.
- Initial-grant configuration change racing with initialization: the strongly consistent snapshot
  issuance is the initialization pricing/configuration linearization point, and the first User DO
  initialization transaction wins. Later configuration cannot regrant.
- Registration outbox failure after local commit, Registry success followed by lost acknowledgement,
  and replay after User DO restart.
- Registry empty query, case-insensitive/prefix identity search, page boundaries, and maximum page
  size.
- Two administrators concurrently changing one account; old/new values follow actual commit order.
- Administrator operation-id same-input replay, changed-input conflict, and changed-actor conflict.
- Grant, deduction, target reconciliation, and reversal all reconcile exactly from the immutable
  Ledger.
- Reverse an already-consumed incorrect grant, observe a negative balance, and prove later paid
  reservation is rejected.
- Attempt to reverse the same original entry with a second operation id.
- Attempt to mutate an unregistered user reference; it must not wake or create that User.
- Exact amount transport above `Number.MAX_SAFE_INTEGER` through real Cap'n Web.
- Proper disposal of every returned nested RPC capability.

## Authorization, privacy, and implementation blockers

Reject the implementation if any of these are present:

- Registry or administrator API creates the initial grant.
- Grant and registration outbox are not in the same User DO transaction.
- An initialized marker is written before a later grant write.
- KV, logs, analytics, or Usage Projection becomes the directory or balance authority.
- Any legacy migration enumerates Durable Object namespaces.
- Administrator RPC accepts an arbitrary username and calls `idFromName()` directly.
- The client supplies actor, server timestamp, a signed delta, or reversal amount.
- The reason is empty or unbounded, or the reason/User identity is copied into logs.
- Reversal edits/deletes the original or recalculates its amount from a current rate.
- A second operation id can reverse the same Ledger Entry twice.
- Administrator mutations use `number` or floating-point financial values.
- Administrator operations bypass #43's single Usage Account module.
- Search returns session tokens, password hashes, provider credentials, prompts, outputs, API
  arguments, headers, or bodies.
- Registry and Usage Projection are one resettable/rebuildable data set.
- A call path can form `AdminSettings -> User DO -> AdminSettings` while the first call waits.
- Tests use only Map/mock storage with no real workerd SQLite and Cap'n Web evidence.
- The slice adds model/Gatekeeper charging, projection reports, CSV, or complete UI pages from later
  issues.

  idempotency. #45 must not create another ledger.

  and does not duplicate pricing configuration.
- #46 through #50 own real model and Gatekeeper Metered Use.
- #51 owns unknown Action-outcome settlement/release reconciliation.
- #62 owns the Usage Projection and administrator overview. The Registry must survive independently.
- #63 owns complete drill-down, filters, and streaming CSV. #45 establishes only the reusable admin
  usage capability, directory search, and accounting mutations.
- #64 consumes #45's activation state for the User surface. It is not part of this slice.
- #65 later deletes identity mappings and anonymizes retained facts. The #45 Registry schema must
  permit identity deletion and must not copy identity into lifetime Ledger facts.
- #66 owns capacity and full-system acceptance.
